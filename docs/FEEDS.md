# Feeds

The files in [`feeds/`](../feeds) follow the format in [`SPEC.md`](../SPEC.md).
The publisher feeds are generated by [`refresh/`](../refresh) and never edited
by hand. A hand edit would be overwritten by the next weekly run, and it would
have no source to point to.

## Sources

| Feed | Dates come from | Current models come from |
|---|---|---|
| `openai.json` | [OpenAI deprecations](https://developers.openai.com/api/docs/deprecations) | the models endpoint (needs `OPENAI_API_KEY`) |
| `anthropic.json` | [Anthropic model deprecations](https://platform.claude.com/docs/en/about-claude/model-deprecations), including "not sooner than" dates for active models | the model overview pages listed in `llms.txt` (no key needed), and the models endpoint when `ANTHROPIC_API_KEY` is set |
| `google.json` | [Gemini API deprecations](https://ai.google.dev/gemini-api/docs/deprecations) | the models endpoint (`GEMINI_API_KEY`; locally `GOOGLE_API_KEY` also works) |
| `mistral.json` | [Mistral models](https://docs.mistral.ai/models) | the models endpoint (`MISTRAL_API_KEY`) |
| `cohere.json` | [Cohere deprecations](https://docs.cohere.com/docs/deprecations) | the models endpoint (`COHERE_API_KEY`) |
| `amazon.json` | Amazon's own models. The entries are carried forward from the committed file; only their `aws-bedrock` dates are refreshed from the [Bedrock lifecycle pages](https://docs.aws.amazon.com/bedrock/latest/userguide/model-lifecycle.html). | |

Distributor dates are added to the publisher feeds as `distributions` entries:

- **Amazon Bedrock**: the [legacy lifecycle table](https://docs.aws.amazon.com/bedrock/latest/userguide/model-lifecycle-legacy.html)
  for models launched before AWS changed its policy on 2026-09-07, and the
  individual [model cards](https://docs.aws.amazon.com/bedrock/latest/userguide/model-cards.html)
  for newer ones. A card's "EOL no sooner than" date becomes a tentative date,
  and an exact Model EOL date stays exact.
- **Vertex AI**: the [model versions page](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/model-versions).
- **Azure AI Foundry**: the [model retirement schedule](https://learn.microsoft.com/en-us/azure/foundry/openai/concepts/model-retirement-schedule),
  matched to the OpenAI, Anthropic, Mistral, and Cohere feeds.

API keys are optional. Without them the refresh still reads every page and keeps
the current models already in the feeds, but it can't add new ones from the
OpenAI, Google, Mistral, or Cohere models endpoints. xAI isn't covered:
it has no lifecycle index, and its models API has no deprecation fields.

How each page is parsed, and what makes a parser stop, is in
[`refresh/README.md`](../refresh/README.md).

## The weekly refresh

[`feed-refresh.yml`](../.github/workflows/feed-refresh.yml) runs every Monday
at 05:23 UTC. It fetches every source, regenerates the feeds, and compares them
with the committed ones.

- **No material change:** the run records a receipt and the hosted feeds'
  `last_checked` time moves forward. Nothing is committed.
- **Material change:** the run opens a PR with a semantic diff (models added,
  dates moved, replacements changed) and an updated freshness line in the
  README. If an earlier refresh PR is still open, nobody else has pushed to it,
  and nobody has approved it or requested changes, the run updates that PR
  instead of opening another. `last_checked` doesn't move while a refresh PR is
  waiting to merge.
- **Parse failure:** the run fails and opens or updates one issue. It never
  writes a partial or guessed feed. The next successful run closes the issue.

A feed's `generated` date changes only when its data changes. `last_checked`
on the public site shows when the sources were last read. The refresh never
drops a model that is in a committed feed; a parser change that would do so
stops the run.

The refresh also removes dates that a source withdraws. In August 2026 Google withdrew
the October 16 shutdown dates it had listed for the Gemini 2.5 Pro, Flash, and
Flash-Lite GA models. The refresh opened
[a PR that removed them](https://github.com/thossullivan/model-eol/pull/60),
and downstream checks stopped warning.

The first feeds were compiled by hand, and the refresh replaced them because
hand-compiled data went wrong quickly. Within the first week of live runs it
caught the Anthropic feed drifting from Anthropic's recommendations and a
Bedrock date that was three months off.

When every commit since the last release changed only feeds or the README,
the merge is released to npm automatically as a patch version, so
`npx model-eol` picks up new dates without a code release. Otherwise the next
release is dispatched by hand.

## Running a refresh locally

```sh
node refresh/refresh.mjs --check            # compare live sources with feeds/
node refresh/refresh.mjs                    # regenerate the publisher feeds
node refresh/refresh.mjs --distributor aws-bedrock,vertex-ai,azure-ai-foundry  # distributor dates
node scripts/feed-changelog.mjs             # render the Atom changelog locally
```

`--check` exits 0 when nothing material changed, 3 when something did, and 1
on failure. `--fixtures DIR` runs against recorded pages instead of the
network. That's what the tests use. Never commit feeds generated from fixtures.

## The public site

[thossullivan.github.io/model-eol](https://thossullivan.github.io/model-eol/)
publishes the feeds with SHA-256 digests, the JSON schemas under canonical
IDs, an Atom changelog of feed changes, a publication manifest, and refresh
health. Each feed is at
`https://thossullivan.github.io/model-eol/feeds/<publisher>.json`, for example
[`feeds/openai.json`](https://thossullivan.github.io/model-eol/feeds/openai.json).

The CLI uses the feeds bundled in its npm package, or a local directory passed
with `--feeds DIR`. The bot can download hosted feeds instead, with
`model-eol-bot --feeds-url URL[,URL...]`. Each download has a 30-second
deadline over the request and body and an 8 MiB body limit. A download that
exceeds either, or returns a feed that fails validation, has failed. A failed
download stops the bot unless `feeds.allow_vendored_fallback` is set (see
[CONFIGURATION.md](CONFIGURATION.md#keys)).

Publication is gated. Each live refresh writes a
[feed-refresh receipt](RECEIPTS.md) with the digest of every feed file. The
Pages workflow publishes only when a receipt matches the feeds on `main`
byte for byte, and afterwards it fetches every deployed file and compares it
with what it meant to publish.
