# Contributing

## Feed corrections

If a feed has a wrong date, is missing a model, or doesn't carry a retirement
you know about, that's the most useful thing you can report.

Don't edit `feeds/*.json` by hand. The files are generated by `refresh/` from
publisher and distributor pages, and the next weekly refresh would overwrite
your change. Instead:

- **The data is wrong or missing and a source says so:** open a
  [feed correction issue](https://github.com/thossullivan/model-eol/issues/new?template=feed-correction.md)
  with the model ID, the channel (the publisher's own API or a distributor), the
  correct value, and the URL that states it. If the parser should have picked
  it up, that URL is the failing test case.
- **A parser missed something:** fix it in `refresh/providers.mjs` or
  `refresh/distributors.mjs`, add a fixture under `refresh/test/fixture/`, and
  regenerate from the live pages with `node refresh/refresh.mjs`. Put the
  semantic diff it prints in the PR description. Don't commit feeds generated
  with `--fixtures`: the fixture's test models and aliases end up in the feed
  as if they were real.
- **A new publisher or distributor:** start from the closest existing parser.
  [`refresh/README.md`](refresh/README.md) explains the rules parsers follow.
  The main one is that a parser that isn't sure must throw. If your change
  makes a parser accept more input, add a test showing it still refuses input
  that would attach a row to the wrong model.

If you work at a model provider, the most useful change is to publish your own
feed at `/.well-known/model-eol.json`. [`SPEC.md`](SPEC.md) is short. Please
open an issue to discuss it.

## Development

You need Node 22 or later and nothing else. There are no dependencies to
install, for the tool or for development.

```bash
git clone https://github.com/thossullivan/model-eol
cd model-eol
npm test
```

| Path | What lives there |
|---|---|
| `check.mjs` | CLI entry point. It only dispatches; the logic is in `lib/`. |
| `lib/` | Scanner, lifecycle dates, config, reports, plan and apply, validation, verify. |
| `bot/` | `model-eol-bot`: plan, evaluate, and publish against the GitHub API. |
| `refresh/` | Feed generation. See [`refresh/README.md`](refresh/README.md). |
| `feeds/` | Generated feeds. |
| `schema/` | Public JSON schemas. |
| `scripts/` | Release, Pages, changelog, and test helpers. |
| `docs/` | Reference docs linked from the README. |

`npm test` runs every suite: checker, refresh, bot, Action, schemas, the
example eval harness, the packed npm package, the changelog, and the public
site. It runs offline with no API keys, and CI runs the same command. For
changes to the scanner or `--changed`, also run the end-to-end harness against
a few real repositories:

```bash
node scripts/e2e-changed.mjs --checker ./check.mjs --repo ../some-repo --repo ../another-repo
```

It replays recent commits through `check --changed` and compares each result
with a full scan of the same commit.

### Tests

Every behavior change needs a test that fails on the old code. Two things
catch people out:

- **Committed feed values change every week.** The refresh workflow runs
  `npm test` against freshly regenerated feeds, so a test that checks a real
  count, date, or `generated` timestamp breaks the weekly refresh. Build a
  small feed inside the test. A test that runs `refresh --check` against the
  committed feeds should accept exit code 0 or 3.
- **Tests don't use the network.** Parsers are tested against recorded pages,
  and fetch functions take an injectable `fetchImpl`.

### Docs that tests check

Some docs are read by tests or rewritten by scripts:

- `README.md` has `<!-- feeds-status -->` markers. The refresh workflow
  rewrites the text between them. Keep the markers.
- `README.md` must contain exactly one Action snippet using
  `actions/checkout@v7` and `actions/setup-node@v7` with `node-version: 22`
  and `package-manager-cache: false`, plus the feed-refresh badge.
- Fragments of the local evaluation script in `docs/BOT.md` are checked by
  `bot/test/package.mjs`. Change the script and the test together.
- `docs/RECEIPTS.md` must document `model-eol verify`.

User-facing basics go in `README.md`, reference material in `docs/`, the feed
format in `SPEC.md`, and parser behavior in `refresh/README.md`.

## Conventions

- **No dependencies,** runtime or development. The test suite fails if one is
  added. Everything the tool runs is in this repository, which keeps it easy to
  audit.
- **Refuse bad input.** Malformed input fails with an error that names the
  problem. It is never replaced with a default or a guess.
- **Comments are one short line** and say what the code can't. Put the
  reasoning in the commit message.
- **No em-dashes in prose.** Use a comma, a colon, parentheses, or a new
  sentence.
- **Write for a public repository.** Commits, issues, and docs contain no local
  paths, private repository names, or personal data.
- Changes to `SPEC.md` or `schema/` start as an issue, not a PR.

## Design decisions

These are settled. To reopen one, open an issue that explains what has changed.
Decisions about the feed format itself are recorded in [`SPEC.md`](SPEC.md).

The checker reports only strings that appear in a feed. It doesn't try to
recognize anything that merely looks like a model name, because false alarms in
CI get a check switched off faster than misses do. Unknown model-like strings
are listed as candidates and never fail or create work.

Cloud and gateway references are hints until something resolves them. Static
analysis can see that code calls Bedrock or OpenRouter but usually can't see
which model sits behind a deployment name, so those references stay in the
inventory and don't fail `--scope direct`. The bot opens an issue for each such
provider instead, so a person can check what is deployed.

Patching is strict. `plan` patches only references it is confident are direct
API calls, and only when the feed's `replacement` is itself safe. Cloud and
gateway references, prose replacements, and dates that came from
`publisher-fallback` become issues for a person.

A distribution entry without a date means nothing is scheduled on that channel.
It doesn't inherit the publisher's date; only a missing entry falls back, and
the result is labeled `publisher-fallback`. An earlier, more cautious reading
told Azure users their models were gone five months early.

`refresh --check` exits 3 only when the generated files change materially.
Rows the parser can't confirm show up in the diff but don't count. Otherwise a
weekly run without API keys would open the same empty PR every Monday, which is
what the first live run did.

model-eol reports when a model stops answering and runs your eval command, but
it doesn't evaluate models itself. The reasons are in
[docs/DESIGN_EVAL_BOUNDARY.md](docs/DESIGN_EVAL_BOUNDARY.md). The eval command
runs only in a job without write access; see
[docs/BOT.md](docs/BOT.md#security-model).

## AI-assisted contributions

Much of this codebase was written by AI models directed by the maintainer, with
adversarial review. When a model wrote or reviewed a change, the commit message
body says so, for example "Implemented by <model>; reviewed by <model>".
Commits don't use `Co-Authored-By` trailers for models.

Contributions are welcome however you write them, on the same terms: you own
what you submit, you've checked it yourself, and it comes with tests. Coding
agents should also read [AGENTS.md](AGENTS.md).

## Security

Please report vulnerabilities privately; see [SECURITY.md](SECURITY.md). Past
adversarial reviews are tracked in issues with the `adversarial-review` label,
and reading them first shows what has already been considered.
